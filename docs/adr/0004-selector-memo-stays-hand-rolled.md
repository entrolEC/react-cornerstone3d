# The selector memo stays hand-rolled — no runtime dependency, no `isEqual`

`useSyncExternalStore` has no selector support, so the hook memoizes the selection itself in a `useRef` keyed by `(Snapshot, selector)`. React ships the same idea as `use-sync-external-store/shim/with-selector` — the `useSyncExternalStoreWithSelector` that react-redux uses — with closure-variable caching and an optional `isEqual`. We evaluated adopting it and decided against it, on three grounds. First, the library has **zero runtime dependencies** (peer deps only) and this would be the first. Second, our `getSnapshot` returns `undefined` when the viewport is absent, which is a normal state (ADR 0002), and the public contract is that the selector is *never called* while it is; `useSyncExternalStoreWithSelector` always calls the selector, so it needs a wrapper, and the wrapper's identity derives from the caller's selector — which for an inline arrow is new on every render, invalidating the `useMemo` that holds their cache. We would land on the behavior we already have, plus a dependency. Third, the one thing it has that we lack is `isEqual`, and structural sharing took away the main reason to want it: a Snapshot rebuild now keeps the references of the parts that did not move, so `s => s.voiRange` is stable with no equality function at all. What remains is a selector that *builds* a value (`s => ({ index, total })`); measured, it re-renders on every Engine event, but it does not loop — the selector is part of the memo key, so the reads React makes within one render agree. A test pins both halves of that. Rejected alongside: opening `isEqual` on `UseViewportStateOptions` anyway, because public API is hard to walk back and nothing has asked for it. Consequence: a value-building selector re-renders more than it needs to; the answer is to select a primitive or an existing sub-object, or to call the hook twice. If that bites, `isEqual` is one comparison at the memo's assignment in `useViewportState.ts`.
