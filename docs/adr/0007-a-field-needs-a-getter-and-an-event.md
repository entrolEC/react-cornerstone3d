# A Snapshot field needs a getter and an event; one Binding kind per getter set

Apps need to know whether an image is in the cache — a stack slider wants to mark each slice loaded or not. That state belongs to Cornerstone3D's cache module, not to a viewport, so 0.4.0 adds a second Binding kind, and we decided three rules to govern every kind. (1) A value becomes a Snapshot field only if the Engine has *both* a getter for it and an event that fires when it changes: the Snapshot is rebuilt on events, so a getter without an event goes silently stale, and an event without a getter would have the library remember state the Engine does not hold (ADR 0001). (2) One getter set, one Binding kind, keyed by what the getters take — a viewportId, an imageId — so the state for a key lives in exactly one place; hooks are surfaces over Bindings, and one kind may have several: `useImageLoadState(imageId)` reads one imageId Binding, `useImageLoadStates(imageIds)` subscribes to N of the *same* Bindings and derives an array (a component cannot call a hook in a loop whose length changes on every `setStack`), and owns no Binding of its own. The library never joins across kinds; the app composes — `useImageLoadStates(useViewportState(id, s => s.kind === 'stack' ? s.imageIds : undefined))` — and ADR 0006's single scheduler guarantees both reads come from the same frame. (3) Every Binding lives only while it has consumers, the same rule for every key; this now includes the viewport Binding that 0.3.0 kept for the session, and it matters most for imageId, since scrolling changes it every slice.

Applied to CS3D 5.10.7, rule 1 leaves exactly one load field: `loaded = cache.isLoaded(imageId)`, invalidated by `IMAGE_CACHE_IMAGE_ADDED` and `IMAGE_CACHE_IMAGE_REMOVED`. The slider wanted four states; two are cut deliberately. *Loading* has a getter (a cache entry with `loaded: false`, created by `putImageLoadObject` at request time) but no event at that moment — the entry appears silently. *Failed* has events (`IMAGE_LOAD_FAILED`, `IMAGE_LOAD_ERROR`) but no getter — the cache deletes the entry, so a failed image reads the same as one never requested, and keeping a failure list in the library would be state the Engine does not hold. Apps that need either listen on `eventTarget` themselves (ADR 0003's path). `loaded` is the cache's word — the image is in the cache — not the viewport's; whether its pixels are on a canvas (`IMAGE_RENDERED`) is out of scope. Also excluded by rule 1: `getImageQuality` (progressive intermediate stages fire nothing), `getMaxCacheSize` / `getBytesAvailable` (set by `setMaxCacheSize`, no event), load cancellation (`cancelLoading`, no event). Not subscribed: `CACHE_SIZE_EXCEEDED` (only ever thrown, never dispatched) and `STACK_VIEWPORT_NEW_STACK` (declared, never fired — `setStack` is caught by `PRE_STACK_NEW_IMAGE`).

The same rule adds two viewport fields with no new events: `currentImageId` (`getCurrentImageId()`; Stack invalidated by `PRE_STACK_NEW_IMAGE`, Volume by `CAMERA_MODIFIED`; `VolumeViewport3D` returns null, normalized to `undefined`) and, on Stack only, `imageIds` (`getImageIds()`, invalidated by `PRE_STACK_NEW_IMAGE`). Two absences stay distinct: `useImageLoadState(undefined)` returns `undefined` without subscribing — there is no question yet (no viewport, no stack) — while an id the cache does not know returns `false` — asked, and not there; `useImageLoadStates([])` returns one stable empty array for the same reason. The return is a bare `boolean`, not `{ loaded }`: with one field, an object would give a selector nothing to select. Deferred, not rejected: `useCacheState()` (`getCacheSize()`, `getVolumes()`) and `VolumeViewportState.volumeIds` wait for a consumer (0.5.0). When they come, `volumeIds` must derive from `getActors()` (`referencedId`), not `getAllVolumeIds()`, whose set is grow-only — `removeVolumeActors` and a second `setVolumes` never remove from it — and a volume's `loading` fails rule 1 the way an image's does.

Consequence for the imageId kind: its Bindings do not attach to Cornerstone3D's `eventTarget` themselves. Its listener list is a plain array — `addEventListener` scans with `indexOf`, `removeEventListener` scans and splices, `dispatchEvent` copies with `slice` — so one listener per image would make `setStack` on a thousand slices quadratic. One dispatcher holds the two listeners and routes each event by imageId to the live Bindings for that id (a Map of the live ones, kept beside the registry: a Binding evicted and subscribed again by the same hook instance is live without holding the key), attaching with the first live Binding and detaching with the last. This holds while `eventTarget` is array-backed; revisit on a CS3D major.


Addendum (2026-10-09, the 0.5.0 grilling): the two deferred items and the roadmap's remaining candidates were checked against CS3D 5.10.7, and 0.5.0 takes the two that have a consumer. *Failed* is built after all — the first field without a getter — under a bounded exception to rule 1 that ADR 0009 states: an event without a getter may become a field when every next word the Engine can say about that key is itself an event the Binding hears (after a failure: `IMAGE_CACHE_IMAGE_ADDED` or `IMAGE_LOAD_FAILED`), so it cannot go silently stale. `useCacheState()` is built as `{ imageBytes }` from `getCacheSize()`, which counts images only; `getMaxCacheSize` stays out as above, and `setPartialImage` is a known silent decrement during progressive loading. (B is implemented in issue 02.) Deferred for want of a consumer, with what the source says: **`volumeIds`** — `getAllVolumeIds()` is grow-only as recorded; legacy classes fire `ACTORS_CHANGED` on every actor mutation while `VOLUME_VIEWPORT_NEW_VOLUME` fires only from `setVolumes`, so `ACTORS_CHANGED` is the event; the Generic Viewport fires no `ACTORS_CHANGED`, and its `removeActors` / `setDisplaySets` / `removeData` fire nothing — a silent write path like ADR 0008's VOI, so on Generic the field would be add-only until CS3D emits on removal. **Annotation state** (`@cornerstonejs/tools`) — ADDED/MODIFIED/REMOVED/COMPLETED on `eventTarget`, state mutated before dispatch, MODIFIED at drag rate; getters keyed FrameOfReferenceUID → toolName, none by viewportId, all returning live objects; silent mutations (`highlighted`, `invalidated`, parent/child links, calibration clearing `cachedStats`) mean only the event-backed subset could be a field; some payloads defeat `structuredClone` (`metadata.enabledElement`, `contour.pointsManager`). When it comes, it lives in a separate entry `react-cornerstone3d/tools` with `@cornerstonejs/tools` as that entry's optional peer, because tools pins core exactly. **Active tool** — the earlier assumption that no mode event exists was wrong: `setToolActive`/`Passive`/`Enabled`/`Disabled` fire `TOOL_MODE_CHANGED` and `setToolActive` also `TOOL_ACTIVATED`, with `getToolOptions` / `getActivePrimaryMouseButtonTool` as getters; only ToolGroup creation and destruction are silent, so an absence contract would need the registry pattern of ADR 0002. **Segmentation** — viewport-keyed getters and mostly paired events; `representationData` replacement and colour-LUT changes are silent, `SEGMENTATION_REPRESENTATION_ADDED` is declared and never dispatched; same entry and pattern as annotations, after them.
