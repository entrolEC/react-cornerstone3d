# Tools state lives in a separate entry; the active tool and the annotation list are its first fields

A viewer's toolbar needs to highlight the active tool and a measurement panel needs the list of annotations, and both have lived in hand-rolled `useEffect` + `eventTarget` listeners in every Cornerstone3D + React app, with the same bug layer as viewport state. That state belongs to `@cornerstonejs/tools`, which pins `@cornerstonejs/core` to an exact version and is not installed by every app that uses core, so we decided the hooks that read it ship from a second entry, `react-cornerstone3d/tools`, with `@cornerstonejs/tools` as an optional peer dependency of the package: the root entry never imports the tools package, and an app that uses only core loads nothing of it. The entry follows ADR 0007's rules unchanged. `useActiveTool(viewportId)` is one Binding kind keyed by viewportId: the getter is `ToolGroupManager.getToolGroupForViewport(viewportId)?.getActivePrimaryMouseButtonTool()` and the events are `TOOL_MODE_CHANGED`, `TOOL_ACTIVATED`, `TOOLGROUP_VIEWPORT_ADDED` and `TOOLGROUP_VIEWPORT_REMOVED`, all on core's `eventTarget`; ToolGroup creation and destruction fire nothing, but a group with no viewport answers nothing and the viewport's arrival is an event, so nothing can go silently stale. `useAnnotations(viewportId, toolName?)` is one Binding kind keyed by (viewportId, toolName): the getter is the annotation state (`getAllAnnotations`, narrowed to the viewport's frame of reference as the enabled element reports it, plus the `isLocked` / `isVisible` / `isSelected` the locking, visibility and selection modules keep) and the events are `ANNOTATION_ADDED` / `MODIFIED` / `COMPLETED` / `REMOVED` and the three flag-change events, plus the viewport's own element events because a new stack or volume changes the frame of reference without an annotation event. An annotation object is live and mutable, and parts of it defeat `structuredClone` (`metadata.enabledElement`, a contour's `pointsManager`), so the Snapshot carries a plain copy of `data` and drops class instances; `highlighted` and `invalidated` change without an event and are not fields (rule 1). Structural sharing is by what the tools package said: an entry is rebuilt when an event named its annotation or a flag set changed, and keeps its reference otherwise, which means a `MODIFIED` that moved nothing still replaces one entry (by value would need a deep compare of `data` on every event; deferred until it costs a visible render). Rejected: putting the hooks in the root entry with a dynamic import (the hooks are synchronous and the first render could not answer); a `kind`-style union over tool state (two getter sets, two Binding kinds, per rule 2); filtering annotation events by frame of reference before scheduling (the frame coalesces the burst, and the rebuild with nothing pending is O(1)); segmentation state in the same release (viewport-keyed getters exist but `representationData` replacement is silent, and it is the next candidate under the same rules). Two facts about the tools package are pinned by `tools.browser.test.ts` and the unit suite: an annotation added by frame of reference fires `ANNOTATION_ADDED` only when some ToolGroup has its tool in a mode (`triggerAnnotationAddedForFOR` returns early otherwise), so such an annotation reaches the hook only on its next event; and `getToolGroupForViewport` throws when several groups claim one viewport, which the hook lets through because Cornerstone3D forbids it. Consequence for CI: the matrix installs `@cornerstonejs/tools` at the same version as core, since tools pins core exactly.


Addendum (2026-10-18, the 0.6.0 defect review): "nothing can go silently stale" was wrong, as ADR 0007's addendum already said of ToolGroup creation and destruction. `useActiveTool` now also hears core's `ELEMENT_ENABLED` and `ELEMENT_DISABLED`, which covers a viewport added to its group before enable (`getToolGroupForViewport` finds the Engine by its viewports, so `TOOLGROUP_VIEWPORT_ADDED` came too early to count) and a group destroyed before its viewport is disabled (the disable finds no group to leave, so `TOOLGROUP_VIEWPORT_REMOVED` never fires). One case stays silent: `destroyToolGroup` (or `ToolGroupManager.destroy()`) while the viewport stays enabled only splices the group out, so the hook keeps the destroyed group's tool until some later event; apps call `removeViewports` first, and `tools.browser.test.ts` pins the silence. The annotation scope is wider than the frame of reference: a viewport whose images have none (CR, DX, US, SC, web images) follows the tools package's own rule for it — of the annotations filed under the `undefined` frame, the ones `viewport.isReferenceViewable(metadata, { withNavigation: true })` accepts — with the stack's `imageIds` array standing in for the frame as the scope, so the list is per stack, not per image, and `VIEWPORT_NEW_IMAGE_SET` rebuilds every entry. The annotation state also changes without an event, through the manager's own methods (`restoreAnnotations`, `addAnnotation`, `removeAnnotation`), `setAnnotationManager` / `resetAnnotationManager` and `cornerstoneTools.destroy()`; loading saved measurements is too common to leave stale, so the entry exports `refreshAnnotations()`, which the app calls after such a change and which marks every live Binding to rebuild every entry in the next frame — still from the Engine's own getters (ADR 0001), only told when to look. The plain copy of `data` turns typed arrays into plain arrays (`Object.freeze` throws on a non-empty one, and CS3D's undo restores a contour as `Float32Array` views) and skips `pointsInShape` / `pointsInVolume` at any depth, as CS3D's own `safeStructuredClone` does, so a drag does not recopy `storePointData`'s samples every frame. Bindings are keyed by `JSON.stringify([viewportId, toolName ?? null])`, so any tool name round-trips.
