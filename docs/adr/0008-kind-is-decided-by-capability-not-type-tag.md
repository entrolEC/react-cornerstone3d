# `kind` is decided by capability, not by the type tag

With `init({ rendering: { useGenericViewport: true } })` (off by default in CS3D 5.10.7), `BaseRenderingEngine` remaps STACK and ORTHOGRAPHIC alike to `ViewportType.PLANAR_NEXT` and instantiates one class, `PlanarViewport`, for both; it still serves the legacy stack getters (`getImageIds`, `getSliceIndex`, `getNumberOfSlices`, `getCurrentImageId`, `getProperties`) through a compatibility controller. `buildSnapshot` picked the Stack branch by `viewport.type === STACK`, so a Generic Stack fell into the Volume branch, and since PLANAR_NEXT was not in the sliced-type set either, `sliceIndex`, `numberOfSlices` and `imageIds` all read `undefined` while camera and VOI survived. We decided that `kind` answers *which slice model the Engine runs* — an index into an image list, or a point along the camera normal — and that this is read from what the viewport can do, never from `viewport.type`. The probes are the ones that actually discriminate in 5.10.7, because method presence alone does not: `BaseVolumeViewport` also has `getImageIds(volumeId)` and every class has `getSliceIndex` (the base throws, VOLUME_3D returns null). A Generic Viewport hosts both models in one class, so it is asked which it holds: `getCurrentMode()` (public `IGenericViewport`) is `'stack'` or `'volume'`, and `'empty'` reads as a stack because its stack getters already answer (an empty list, index 0), the same as a legacy Stack before `setStack` — so a Generic ORTHOGRAPHIC viewport is an empty Stack until `setVolumes` flips it. Legacy classes hold one model each, and only `StackViewport` takes a stack: `typeof setStack === 'function'`. Slice Position is likewise read, not probed: a viewport whose `getSliceIndex` reports no number has none, and `getNumberOfSlices` is not asked (VOLUME_3D would say 1); this also lets Video and WSI report their frame index, which the old type set withheld. Rejected: adding `kind: 'planar'` (every consumer narrowing on `kind` would have to change for a rendering-engine flag that changes nothing they read); adding PLANAR_NEXT to the sliced-volume set (Slice Position comes back but `imageIds` stays lost, and a Generic Stack would read as `'volume'`, breaking `s.kind === 'stack' ? s.imageIds : undefined`); reading `viewport.requestedType` (the tag CS3D keeps beside the remap — a tag again, and it cannot say which model a dual-mode class holds now). Consequence for ADR 0007's rule 1: `PlanarViewport` fires no `PRE_STACK_NEW_IMAGE` at all — a slice change or a new stack goes through `setViewState`, which fires `CAMERA_MODIFIED` synchronously, so the existing event list covers it — but the legacy write `setProperties({ voiRange })` ends in `setDataPresentationState`, which renders and fires nothing: the getter moves and no element event says so. The Engine's getter/event pair for VOI exists (`getProperties` / `VOI_MODIFIED`), only the legacy write path skips the event; the hook cannot hear a silent write (ADR 0001), so under the Generic Viewport an app writes VOI with `setDisplaySetPresentation({ voiRange })`. Both facts are pinned by `useViewportState.generic.browser.test.ts`, which runs the Stack and Volume smoke cases with the flag on (`init` takes its config once per module, so the flag needs its own file); the legacy suite keeps running the same cases with it off. This rests on `getCurrentMode` staying the Generic Viewport's word for its content and on `setStack` staying unique to the legacy Stack class; a CS3D major revisits both probes.
